# 01 技术选型

> 状态：v0.3（决策落地）· 2026-11-05  
> 版本号均为 2026-11-05 npm 查询结果；落地时以 lockfile 固定，不盲目追 latest。v0.2 复核后轻微漂移：Biome 2.6.5、Vite 8.3.6、lucide-solid 1.69.0（以 lockfile 为准）。

---

## 1. 背景与约束

| 维度 | 假设 |
| --- | --- |
| 使用场景 | 企业内部中后台：表单、列表、详情、审批、权限、报表入口 |
| 团队 | 3–4 名前端 + 1 名设计/视觉评审（可兼职）+ 0.5 QA/自动化（可调整） |
| 技术栈 | 新项目以 SolidJS 为主；可能并存 Vite / Webpack 5 / Rspack / SolidStart |
| 运行环境 | 桌面端为主，Chrome / Edge 为主；Firefox / Safari best effort；可能运行在微前端容器中 |
| 交付 | 私有 npm registry，内部文档站，长期维护 |
| 非目标 | 不做低代码设计器、不做图表库、不做富文本编辑器内核、不追求覆盖 AntD 全量组件 |

选型优先级：**稳定可维护 > 企业场景匹配 > 无障碍与可测试性 > 开发体验 > 包体积**。

> Ant Design / Semi Design 是 React-only，TDesign 目前没有官方 Solid 版本。用 Web Components 包装会引入 SSR、主题、事件、类型和表单集成问题，因此选择自研 Solid 组件层，而不是二次包装现有库。

---

## 2. 选型原则

1. **稳定优先**：生产基线不采用 RC / alpha；预发布版本只用于 Spike。
2. **Solid 原生**：组件必须利用 Solid 的细粒度响应式；不引入 React 运行时或框架无关的 Web Components 作为核心。
3. **不重复造轮子，但核心 API 自主**：无障碍原语、表格状态机、日期算法用成熟库；Form / Table / DatePicker 的**对外 API 和渲染**由我们控制。
4. **样式可预测**：构建期 CSS + CSS 变量；消费者可覆盖、可主题化、可微前端隔离；避免运行时样式注入。
5. **企业能力前置**：SSR、i18n、RTL、暗色、密度、多品牌、A11y、微前端从第一天纳入设计，而不是后补。
6. **可迁移**：对 Solid 2.0、Vite / TypeScript 未来版本保留隔离层，避免全局耦合。

## 4. 关键决策与对比

### 4.1 SolidJS：1.9 稳定版，而不是 2.0 RC

**决策：生产基线使用 `solid-js@1.9.x`，Phase 0 只做 2.0 兼容性评估。**

理由：

- `2.0.0-rc.*` 已存在，但 Kobalte 0.13、`@solidjs/testing-library`、SolidStart 2.2 等生态仍以 1.9 为主；SolidBase 2.0 甚至要求 Solid 2.0 RC，说明生态处于分裂期。
- 企业组件库的首要风险是“底层运行时升级导致全量回归”，不是“晚半年用上新特性”。
- 1.9 的细粒度响应式、`createUniqueId`、`isServer`、`Suspense` 等已足够支撑中后台。

迁移策略：

- 所有对 `solid-js/web` 的依赖（`Portal`、`isServer`、`render`、`hydrate`）集中到 `src/utils/dom.ts` 一个适配层，Solid 2.0 若拆分 `@solidjs/web`，只改这一处。
- 不使用可能在 2.0 移除的隐式 API；CI 增加一个可选的 2.0 RC 兼容 job（不阻塞发布）。
- 在 v1.x 内保持 Solid 1.9 peer 范围；2.0 稳定后再评估 v2.0。

### 4.2 TypeScript 7 + oxlint / Biome：替换 typescript-eslint

**决策：`typescript@7.0.2` 用于类型检查与声明产出；移除 ESLint / typescript-eslint / eslint-plugin-solid / eslint-config-prettier，lint 改为 `oxlint + oxlint-tsgolint`（类型感知）与 `@biomejs/biome`（Solid 专项）。**

理由：

- 用户要求 TypeScript 7+；`typescript-eslint@8.72.1` 的 peer 范围是 `>=4.8.4 <6.1.0`，canary 也没有稳定的 TS 7 支持。
- TS 7 是原生编译器路线，包只导出 `version` 与 `unstable/*` API，不再提供 typescript-eslint 依赖的旧 compiler API，因此 **type-aware ESLint 不可行**。
- `oxlint@1.91.0` + `oxlint-tsgolint@7.0.2005` 使用 TypeScript 7 的原生编译器（typescript-go）做类型感知规则，支持 JSX/TSX，速度远高于 JS 实现的 lint。
- `@biomejs/biome@2.6.4` 提供 `solid` domain，包含 `noSolidDestructuredProps`、`useSolidForComponent`、`noReactSpecificProps` 等规则，可替代 `eslint-plugin-solid` 的核心约束。
- `ts-morph` 依赖 TS 旧 compiler API，TS 7 下不可用；API 表生成改用 `oxc-parser`（与 oxlint 同属 Oxc，直接解析 TSX AST，不依赖 TS compiler API）。

策略：

- `pnpm lint` 由三部分组成：
  - `oxlint --type-aware`：通用 + 类型感知规则；
  - `biome lint`：仅启用 `solid` domain，显式配置 `linter.domains.solid = "all"`、`linter.rules.recommended = false`，`formatter.enabled = false`；
  - `stylelint`：SCSS 规范。
- `pnpm typecheck` 使用 `tsc --noEmit`；Phase 0 评估 `oxlint --type-aware --type-check` 是否能替代一次 tsc pass，不替代声明产出。
- 不使用 `baseUrl`（TS 7 / tsgolint 不支持）；路径别名统一用 `paths` + `moduleResolution: bundler`。
- 不使用依赖 TS 旧 compiler API 的工具；API 表生成用 `oxc-parser`，复杂继承/类型别名无法静态推导时允许手工 `api.ts` 补充。
- 不再引入 ESLint 插件生态；若未来必须使用某个 ESLint 插件，单独评估 oxlint 的 JS plugin 支持（alpha），不默认依赖。
- **TS 7 分发形态（v0.2 实测补充）**：`typescript@7.0.2` 的 `tsc` 是 JS wrapper，实际编译器为 20 个 `@typescript/typescript-<platform>` 原生二进制包（optionalDependencies）。私有 registry 必须镜像这些平台包，CI 容器架构要与可用平台包对齐；未镜像时报错 `Unable to resolve @typescript/typescript-darwin-arm64`。
- **tsconfig 硬性约束（v0.2 实测补充）**：`baseUrl` 已移除（TS5102）；`rootDir` 必须显式设置（TS5011）；`include` 必须收窄为 `["src/**/*"]` 并配 `skipLibCheck`，否则会误扫 `node_modules` 内的 `.d.ts` 报大量错。`tsc --emitDeclarationOnly`、`declarationMap`、`jsx: preserve + jsxImportSource`、`paths`（无 baseUrl）均已实测通过。
- Solid 规则覆盖以 Biome `solid` domain 为准；未覆盖的响应式约定（如用 `createMemo` 代替 `createEffect`）继续通过 review checklist 与文档约束。

### 4.3 样式：SCSS + CSS 变量 + BEM

**决策：组件库作者态用 SCSS（嵌套、mixin、函数），构建为普通 CSS；主题全部通过 CSS Custom Properties；类名 BEM + 固定前缀；不使用运行时 CSS-in-JS、Tailwind / UnoCSS。**

理由：

| 方案 | 优点 | 问题 | 结论 |
| --- | --- | --- | --- |
| SCSS + CSS 变量 + BEM | 零运行时；SSR 简单；CSP 友好；消费者可用普通 CSS 覆盖；微前端隔离可控 | 需要自建 token/主题管线；BEM 命名需纪律 | **采用** |
| CSS-in-JS（Emotion / AntD cssinjs） | 动态主题方便；样式与组件同文件 | 运行时开销、SSR 抽取、CSP、微前端重复注入、调试成本 | 拒绝 |
| Tailwind / UnoCSS | 开发快；原子化 | 作为**发布型组件库**，消费者需扫描 node_modules 或全量引入；类名冲突；覆盖成本高 | 拒绝（应用侧可自行使用） |
| CSS Modules | 局部作用域；无全局冲突 | 哈希类名不利于消费者覆盖；主题与变体组合不够直观 | 不作为主方案 |
| vanilla-extract | 构建期、类型安全 | 额外工具链；团队熟悉度低；与 TSX 设计 spec / SCSS 协作不直接 | 暂不采用 |

实现约定：

- 类名（v0.2 统一）：BEM 只用于静态结构 —— `.ui-button`、`.ui-button__icon`；**变体 / 尺寸 / 状态改用 `data-*`**（`data-variant` / `data-color` / `data-size`），不再使用 `.ui-button--primary` / `.ui-button--sm` 这类 modifier class；尺寸取值统一 `small | medium | large`。
- 低特异性：组件根节点尽量用 `:where(.ui-button)` 包裹，方便业务侧覆盖；内部状态用 `data-*`：
  `data-size`、`data-variant`、`data-disabled`、`data-state="open|closed"`。
- 不使用 `!important`；不写全局 `body` / `html` 样式；reset 作为**可选**入口。
- 暗色：`[data-ui-theme="dark"]`；密度：`[data-ui-density="compact"]`；RTL：`dir="rtl"` + 逻辑属性。
- 微前端：固定前缀、低特异性、无全局副作用；portal 容器可配置。

### 4.4 无障碍原语：Kobalte，而不是 Ark UI / 自研

**决策：以 `@kobalte/core@0.13.x` 为底层原语，封装在内部 `src/primitives/` adapter 中；缺失的复杂组件自研。**

理由：

- Kobalte 是 Solid 原生、专为 design system 设计的 headless 库，覆盖 Dialog、Popover、Select、Combobox、Menu、Tabs、Tooltip、Toast、Checkbox、Switch、Slider、RadioGroup、NumberField、Pagination 等高频组件。
- 发布形态是**编译后 JS + 保留 JSX 源码的双构建**：`"solid"` 条件给消费方按 SSR / CSR 目标重新编译，`import` 条件给普通 SPA / MPA 直接使用；`dist/source/*.jsx` 是已转译掉 TS、仅保留 JSX 的源码产物，消费方无需处理 TSX。
- 2026-10 仍在维护（0.13.14）。

对比：

| 方案 | 结论 | 原因 |
| --- | --- | --- |
| Kobalte | **采用** | Solid 原生、编译产物、A11y 覆盖好、API 适合 design system |
| Ark UI Solid 5.40 | 不采用 | `exports` 直接指向 `src/*.tsx`，要求消费方编译 node_modules；对 Webpack / Rspack / 企业构建不友好 |
| 自研全部原语 | 不采用 | A11y、焦点管理、键盘导航成本极高，3–4 人团队不现实 |
| SUID / Park UI | 不采用 | 视觉与 API 绑定 MUI / Panda，二次设计成本高；适合参考实现 |
| Corvu | 不采用 | 最后发布 2025-01，维护活跃度不足 |

风险与对策：

- Kobalte 仍是 0.x，API 可能变化：**内部 adapter 只暴露我们自己的 props**，升级只改 adapter。
- Kobalte 缺口：DatePicker / Calendar、TreeView、Cascader、Table、Upload、Form、Anchor、Affix、Watermark、QRCode。这些自研。
- 若 Kobalte 停止维护：adapter 层可逐步替换为自研或 fork；不直接把 Kobalte 类型泄漏到公共 API。

### 4.5 表格：TanStack Table v9 + Virtual

**决策：使用 `@tanstack/solid-table@9.x` 管理排序/过滤/分组/分页/列状态，使用 `@tanstack/solid-virtual` 做虚拟滚动；`Table` 的 DOM、样式、列配置 API 自研。**

理由：

- 企业表格的难点是状态模型（多列排序、过滤、分组、列固定、列宽、选择、展开、树形），不是 DOM。
- TanStack Table 框架无关、MIT、可 tree-shake；v9 是当前稳定线。
- AG Grid Community 虽强，但体积大、主题体系独立、企业功能（服务端行模型、Master/Detail 等）与我们的设计系统耦合差；不采用。

风险：

- v9 相对新，API 与 v8 差异大；用内部 `useTableEngine` 包一层，若 v9 有问题可回退 v8.5.x，不影响公共 API。
- 虚拟滚动 + 固定列 + 动态行高是难点，MVP 先固定行高，v1.0 再支持动态测量。

### 4.6 日期：`@internationalized/date` + 自研 Calendar

**决策：日期算法用 Adobe 的 `@internationalized/date`，Calendar / DatePicker / RangePicker / TimePicker 自研。**

理由：

- 原生 `<input type="date">` 无法满足企业级交互、范围选择、禁用规则、快捷选项、时区与中文体验。
- flatpickr 等 DOM 插件难以与 Solid 受控状态、主题、A11y、SSR 深度集成。
- Ark UI 的 DatePicker 受其源码发布方式限制，不引入。
- `@internationalized/date` 提供不可变日期对象、时区、locale、日历系统，适合做底层。

API 约定（待评审）：

- 对外主类型使用原生 `Date`（业务开发者最熟悉）；内部转换为 `CalendarDate` / `ZonedDateTime`。
- 支持 `value` / `defaultValue` / `onChange`、`min` / `max`、`disabledDate`、`presets`、`format`、`showTime`、`timeZone`。
- 范围选择用 `[Date, Date]`；清空为 `null`。
- 不在组件内部隐式使用 `new Date()` 作为 SSR 初始值，避免 hydration mismatch。

### 4.7 表单：自研轻量引擎，保留切换 TanStack Form 的可能

**决策：v1 自研 `createForm` / `Form` / `Form.Item`，API 对齐 AntD 的使用习惯；Phase 0 用 2 天对比 TanStack Form，若自研成本超预期则替换内核、保持外层 API。**

理由：

- 表单是业务系统最高频、最需要深度定制的组件：布局、校验、联动、动态字段、错误滚动、与 Upload/Select/DatePicker 集成。
- AntD 风格的 `Form.Item name` + 子控件自动注入是团队最熟悉的写法；需要 `FieldContext` 机制。
- TanStack Form 1.33 活跃，但 Solid adapter 的生态验证不如 React；直接暴露其 API 会增加学习成本。

v1 必做能力：

- `initialValues`、`onFinish` / `onFinishFailed`、`validateFields`、`resetFields`、`setFieldsValue`、`getFieldsValue`。
- `Form.Item`：`name`（支持路径）、`label`、`rules`、`required`、`validateTrigger`、`help`、`extra`、`status`。
- 规则：required、min/max、pattern、type、自定义同步/异步 validator；可选 Zod / Valibot resolver。
- 布局：horizontal / vertical / inline；label 宽度、冒号、必填标记。
- `Form.List` 动态字段、`dependencies`、`shouldUpdate` 放 v1.0。
- 性能：字段级订阅，避免任一字段输入触发整表重渲染。

### 4.8 文档站：自建 Vite + Solid SPA

**决策：`apps/docs` 用 Vite + Solid + `@solidjs/router`，页面用 TSX；Demo 用 `import.meta.glob` 直接加载并展示源码；API 表用 `oxc-parser` 生成；搜索用 Fuse.js；代码高亮用 Shiki。**

理由：

| 方案 | 结论 | 原因 |
| --- | --- | --- |
| 自建 Vite + Solid | **采用** | 与组件库同运行时；Demo 可直接 import；完全控制主题/密度/RTL 切换；无额外框架 |
| Storybook | 不采用 | `storybook-solidjs` 仍是 beta；企业内维护成本高 |
| SolidBase 2 | 不采用 | peer 要求 Solid 2.0 RC，与 1.9 基线冲突 |
| MDX（solid-mdx） | 暂不采用 | `solid-mdx` 0.0.7，成熟度不足；文档以 Demo + API 表为主，TSX 足够 |
| Astro / VitePress | 不采用 | 引入第二框架；跨 island 共享 ConfigProvider / 主题上下文复杂 |

后续若需要 SSG / SEO：迁移到 SolidStart 2.2.x（当前 peer 支持 Solid 1.9.15 + Vite 8），或给现有 SPA 加预渲染。文档站是内部使用，SSG 不是 v1 阻塞项。

### 4.9 测试：Vitest + Playwright，不依赖过时 A11y 插件

- **单元/行为**：Vitest 5 + `@solidjs/testing-library` + jsdom + `@testing-library/user-event`。
- **真实浏览器**：Playwright 1.64 + `axe-core`；覆盖键盘、焦点、弹出层定位、虚拟滚动、截图。
- **视觉回归**：Playwright `toHaveScreenshot`，CI 用官方 Docker 镜像固定字体/渲染；基线随 PR 审核。
- **SSR（MVP）**：`renderToString` 快照 + `examples/solid-start` 构建、SSR 渲染与 hydration 冒烟（light / ltr / default 单档），CI 检查 hydration warning；**v1.0** 再补暗色 / 紧凑 / RTL 全矩阵与流式渲染。
- **消费方冒烟**：`examples/vite`、`examples/webpack`、`examples/rspack` 三个最小应用验证 exports / CSS / 类型 / tree-shaking；`examples/solid-start` 验证 `"solid"` 条件解析、SSR 渲染与 hydration。
- **Rspack 消费方**：`examples/rspack` 使用 `@rspack/core` 2.3.x + `@rspack/cli`；Solid 1.9 的 TSX 通过 `babel-loader` + `babel-preset-solid` 转换（Rspack 内置 SWC 暂不覆盖 Solid JSX transform），验证 exports / CSS / 类型 / tree-shaking 与 Vite、Webpack 行为一致。
- **包质量**：`publint`、`attw`、`size-limit` 作为 CI 门禁。

不采用 `vitest-axe`（0.1.0，维护不足）；A11y 扫描放在 Playwright 真实浏览器中，单元测试专注键盘与焦点行为。

### 4.10 Lint / 格式化 / 发布

- **oxlint 1.91.0 + oxlint-tsgolint 7.0.2005**：类型感知 lint，基于 TS 7 原生编译器；覆盖 correctness / suspicious / perf / typescript 规则。只启用与 Prettier 不冲突的规则。

## 5. 浏览器与运行时基线

**基线：Chrome 最近 30 个稳定版。以 2026-11-05 的 Chrome 157 计算，约为 Chrome 128–157；Edge 跟随 Chromium；Firefox / Safari 为 best effort（建议 Firefox 128+ / Safari 17.6+），不作为发布阻塞；不支持 IE / 旧 Chromium / 360 兼容模式。**

可用能力（Chrome 128+ 全部支持）：

- CSS：Custom Properties、Flexbox、Grid、Subgrid、`:where()`、`:has()`、`:focus-visible`、`gap`、`aspect-ratio`、`@layer`、`color-mix()`、Container Queries、CSS Nesting、逻辑属性、`text-wrap: balance`、`@starting-style`。
- JS：`ResizeObserver`、`IntersectionObserver`、`Intl`、`matchMedia`、`AbortController`、`structuredClone`、`Promise.withResolvers`、`Array.prototype.at`、`Object.hasOwn`。
- 模块：ESM、`import.meta`、动态 import、top-level await。

策略：

- 组件库主样式可以直接使用上述现代 CSS；不再为 Chrome 128 以下做语法降级。
- Firefox / Safari best effort：用 `@supports` 提供关键回退（如 `color-mix()` 的回退 hex、`@layer` 缺失时的普通层叠），但不保证像素级一致。
- `browserslist`：`chrome >= 128`、`edge >= 128`、`firefox >= 128`、`safari >= 17.6`；PostCSS 只做必要前缀与渐进增强，不引入 `:has()` polyfill。
- **滚动窗口的同步动作（v0.2 补充）**：「最近 30 个稳定版」是滚动基线，每季度复核后必须同步更新 `browserslist`、PostCSS 目标、Playwright 浏览器版本与 `examples/*` 冒烟矩阵，并在 CHANGELOG 标注；仅写死 `chrome >= 128` 会导致基线漂移无人维护。
- 主题色阶仍在构建期生成 hex，作为稳定运行时值；`color-mix()` 可用于业务侧渐进增强，不作为 token 的唯一来源。
- 若业务确需 360 / 旧 Chromium：作为独立兼容层评估（单独构建 + 降级样式），不进入主基线。
- Phase 0 用真实 Chrome / Edge 做一次渲染/交互验收；Firefox / Safari 做冒烟。

## 6. SSR / 微前端 / 安全约束

> 定位（v0.3 修订 / ADR-018）：**试点主力 SPA / MPA（CSR），不强依赖 SolidStart；但组件库必须保证 SSR 场景使用正常** —— 服务端 `renderToString` 不抛 `Client-only API called on the server side`，hydration 无 mismatch / console warning。因此 `"solid"` 条件导出 + `dist/source/*.jsx` 源码产物是 **MVP 必备产物**，不是 v1.0 前置。微前端仍是 best effort，不阻塞 MVP。

### SSR

**为什么必须双构建（依据 vite-plugin-solid 官方文档）**：Solid 在构建期把 JSX 编译为不同目标的产物（客户端 DOM / 服务端 SSR / 可 hydrate），只发布编译后 JavaScript 等于把目标锁死。官方明确：这种产物是 *client-only DOM code that cannot hydrate*；解法是发布带 `"solid"` 条件的 JSX 源码，由消费方按自身目标重新编译。

- **MVP 产物**：`{ "solid": "./dist/source/*.jsx", "import": "./dist/*.js" }` 双入口，**每个含组件的导出都要有对应的 `solid` 条目**；Phase 0 做可行性 Spike，Phase 1 建成正式构建，M4 验收（见 [02 §3.3](./02-架构设计.md#33-solid-条件导出)）。
- **MVP 验收**：`examples/solid-start` 构建 + `renderToString` + hydration 冒烟（light / ltr / default 单档），CI 检查 hydration warning；三端（Vite / Webpack 5 / Rspack）冒烟照旧。
- **SSR-safe 编码升为 MVP 验收项**：模块顶层不访问 `window` / `document` / `matchMedia`；用 `isServer`、`onMount`、`createUniqueId`；ID 确定性。v0.2「仅约束、不验收」的口径作废。
- **v1.0 范围**：暗色 / 紧凑 / RTL 全矩阵的 SSR 回归、流式渲染、Portal 类组件（Modal / Drawer / Tooltip / Select popup）SSR 行为细则、已知限制清单。
- `ConfigProvider` 的主题属性由应用在 HTML 上预设，避免首屏闪烁（客户端同样适用）。

### 微前端

- `solid-js` 必须是 **peerDependency + 单例**；qiankun / wujie / Module Federation 中共享同一份 Solid，避免 Context 断裂。
- `@ui-design/core` 也建议单例共享；至少保证同一页面只加载一个版本。
- CSS：固定前缀、低特异性、无全局 reset、无 `body` 样式；`ConfigProvider` 支持 `themeTarget` 与 `portalContainer`。
- 提供 qiankun / wujie / Module Federation 集成示例与已知问题清单；不作为 MVP 阻塞项。

### 安全 / CSP

- 不通过 JS 注入 `<style>`；CSS 由构建产物提供。
- 运行时主题变量通过 `style` 属性设置 CSS 变量，严格 CSP 下需要 `style-src 'unsafe-inline'` 或改用预生成主题 class；在文档中明确。
- 默认按文本渲染；`Typography` 的 HTML 渲染必须显式开启，并建议调用方自行 sanitize。
- 不引入外部 CDN 字体/图标；所有资源随包发布。

## 7. 被否决的方案（速查）

| 方案 | 否决原因 |
| --- | --- |
| Solid 2.0 RC 作为基线 | 生态未稳定；Kobalte / Testing Library / SolidBase 版本分裂 |
| TypeScript 6.x + typescript-eslint | 用户要求 TS 7+；typescript-eslint 不支持 TS 7，且 TS 7 不再暴露旧 compiler API |
| ESLint + typescript-eslint | 无法在 TS 7 下做 type-aware lint；改由 oxlint / tsgolint 承担 |
| `ts-morph` 生成 API 表 | 依赖 TS 旧 compiler API，TS 7 下不可用；改用 `oxc-parser` |
| 运行时 CSS-in-JS | SSR / CSP / 微前端 / 性能成本 |
| Tailwind / UnoCSS 作为组件库样式层 | 发布型库的类名冲突、消费者扫描 node_modules、覆盖困难 |
| Ark UI Solid | 源码 TSX 发布，消费方需编译 node_modules |
| SUID / Park UI | 视觉与 API 锁定 MUI / Panda，不适合自有设计系统 |
| Storybook | Solid adapter beta，维护成本高 |
| SolidBase 2 / solid-mdx | 分别依赖 Solid 2 RC / 成熟度不足 |
| AG Grid | 体积、主题体系、企业功能耦合 |
| flatpickr / 原生 date input | 交互、主题、A11y、SSR 不满足 |
| 自研全部无障碍原语 | 成本与风险过高 |
| MVP 只发编译后 ESM 却要求 SSR 可用 | 否决（v0.2 提出、v0.3 执行）：产物无法 hydrate；改为 MVP 即发布 `"solid"` 条件导出 + JSX 源码双构建 |

## 8. 版本与升级策略

- **锁文件为准**：CI 使用 `pnpm install --frozen-lockfile`；不在 CI 动态取 latest。
- **Renovate / Dependabot**：每周 patch，每月 minor；major 单独 PR + 回归。
- **Solid**：1.9.x 内跟进 patch；2.0 稳定后再评估，适配层先行。
- **TypeScript**：7.0.x；跟随 patch；不降级 6.x。`baseUrl` 等旧选项迁移到 `paths` + `moduleResolution: bundler`。
- **oxlint / oxlint-tsgolint**：同 major 跟进；tsgolint 要求 TS 7+，升级 TS 时先跑 `oxlint --type-aware`。
- **Biome**：2.x；`solid` domain 规则随版本更新，升级后检查规则变更。
- **Kobalte**：0.13.x 内跟进；minor 升级必须跑完整 A11y + 视觉回归。
- **Vite / Vitest**：同 major 内跟进；Vite 8 → 9 需验证 `vite-plugin-solid` peer 与 CSS 产物。
- **浏览器基线**：Chrome 最近 30 个稳定版；每季度复核一次，变更视为 minor，需在 CHANGELOG 标注，并同步 `browserslist` / PostCSS / Playwright / 冒烟矩阵。
- **TS 7 平台包**：升级 typescript 时必须同步镜像对应版本的全部平台包，并在 CI 各架构验证 `tsc --version` 可运行。
