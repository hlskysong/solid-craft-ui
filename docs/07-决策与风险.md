# 07 决策与风险

> 状态：v0.3（决策落地）· 2026-11-05  
> 本文记录关键技术决策（ADR 摘要）、风险登记、待确认问题与假设。后续每次重要决策在此追加，不覆盖历史。

## 1. 架构决策记录（ADR）

### ADR-001：生产基线使用 SolidJS 1.9.x

- **状态**：已决定（待 Phase 0 复核）
- **背景**：Solid 2.0 RC 已存在，但 Kobalte 0.13、Testing Library、SolidStart 2.2 等仍以 1.9 为主；SolidBase 2 已转向 2.0 RC，生态处于分裂期。
- **决策**：v1 以 `solid-js@1.9.x` 为生产基线；2.0 仅做兼容性评估。
- **后果**：
  - 稳定、生态成熟；短期无法使用 2.0 新特性。
  - 需要 `solid-js/web` 适配层，为未来拆分 `@solidjs/web` 做准备。
  - 2.0 稳定后需要一次迁移评估（可能影响包导出与 SSR）。
- **替代方案**：直接上 2.0 RC（拒绝：生产风险）；等待 2.0 稳定（拒绝：无法启动）。

### ADR-002：TypeScript 7.0.x + oxlint / Biome lint

- **状态**：已决定（Phase 0 复核工具链）
- **背景**：用户要求 TS 7+；`typescript-eslint@8.72.1` peer 要求 `>=4.8.4 <6.1.0`，且 TS 7 只暴露 `version` 与 `unstable/*` compiler API，ESLint 无法做 type-aware lint。
- **决策**：`typescript@7.0.2` 负责类型检查与声明产出；lint 改为 `oxlint@1.91.0 + oxlint-tsgolint@7.0.2005`（类型感知，基于 TS 7 原生编译器），Solid 专项规则由 `@biomejs/biome@2.6` 的 `solid` domain 承担；移除 ESLint / typescript-eslint / eslint-plugin-solid / eslint-config-prettier。
- **后果**：
  - 获得 TS 7 原生编译速度与类型感知 lint；不再依赖 ESLint 插件生态。
  - Solid 规则覆盖以 Biome `solid` domain 为准；未覆盖的响应式约定需 review。
  - `ts-morph` 等依赖旧 compiler API 的工具需替换（API 表改用 `oxc-parser`）。
  - TS 7 不支持 `baseUrl` 等旧选项，需要迁移 tsconfig。
- **替代方案**：TS 6 + typescript-eslint（拒绝：不满足 TS 7 要求）；TS 7 + 取消 lint（拒绝：质量下降）；TS 7 + ESLint canary（拒绝：无稳定支持）。

### ADR-003：SCSS + CSS Custom Properties + BEM

- **状态**：已决定
- **背景**：需要 SSR、CSP、微前端隔离、消费者覆盖、暗色/密度/品牌主题。
- **决策**：作者态 SCSS，构建为普通 CSS；主题通过 CSS 变量与 `data-*`；类名 BEM + 固定前缀；不使用运行时 CSS-in-JS / Tailwind。（**v0.2 由 ADR-015 细化**：BEM 仅用于静态结构，可枚举变体与状态统一用 `data-*`，尺寸统一 `small | medium | large`。）
- **后果**：
  - 无运行时样式开销；SSR/微前端友好；覆盖成本低。
  - 需要自建 token/主题管线与 BEM 纪律。
  - 不能像 CSS-in-JS 那样在组件内动态生成任意样式。
- **替代方案**：CSS-in-JS（拒绝：运行时/SSR/CSP）；Tailwind（拒绝：发布型库冲突）；CSS Modules（拒绝：覆盖不便）。

### ADR-004：Kobalte 作为无障碍原语

- **状态**：已决定（0.x 风险需持续跟踪）
- **背景**：自研全部原语成本过高；Ark UI Solid 以源码 TSX 发布，消费方需编译 node_modules；SUID/Park UI 视觉与 API 锁定。
- **决策**：使用 `@kobalte/core@0.13.x`，封装在 `src/primitives/`；公共 API 不暴露其类型。
- **后果**：
  - 快速获得 Dialog / Select / Menu / Tabs / Tooltip 等 A11y 能力。
  - 0.x API 可能变化；缺口组件需自研。
  - 需要 adapter 层与升级回归测试。
- **替代方案**：Ark UI（拒绝：打包方式）；自研（拒绝：成本）；Corvu（拒绝：维护停滞）。

### ADR-005：Table 使用 TanStack Table v9 + Virtual

- **状态**：已决定（v9 新，保留回退 v8 的可能）
- **背景**：企业表格状态复杂；自研状态机成本高；AG Grid 体积与主题体系不匹配。
- **决策**：TanStack Table 管理排序/过滤/分组/分页/列状态，自研 DOM、样式、列配置 API；TanStack Virtual 做虚拟滚动（**虚拟滚动为 v1.0 能力，MVP 不引入该依赖**）。
- **后果**：
  - 复用成熟状态模型；保留视觉与 API 控制。
  - v9 API 较新，需要内部 `useTableEngine` 隔离；固定列/虚拟滚动/动态行高仍需大量工作。
- **替代方案**：AG Grid（拒绝）；完全自研（拒绝：周期长）。

### ADR-006：DatePicker 自研 + `@internationalized/date`

- **状态**：已决定
- **背景**：原生 date input 体验不足；flatpickr 难以深度集成；Ark UI DatePicker 受打包方式限制。
- **决策**：日期算法用 `@internationalized/date`，Calendar / DatePicker / RangePicker / TimePicker 自研。
- **后果**：
  - 完全控制交互、主题、A11y、SSR。
  - 工作量大（XL），范围/时间/时区需分阶段。
- **替代方案**：flatpickr（拒绝）；Ark UI（拒绝）；原生（拒绝）。

### ADR-007：Form 自研轻量引擎

- **状态**：已决定（Phase 0 对比 TanStack Form）
- **背景**：表单是业务核心，需要 AntD 风格 API、布局、校验、联动、动态字段、控件集成。
- **决策**：自研 `Form` / `Form.Item` / `useForm` + `FieldContext`；可选 Zod/Valibot resolver；Phase 0 用 2 天评估 TanStack Form，若自研超预期则替换内核、保持 API。
- **后果**：
  - API 自主、体验一致；需要投入 4–6 周。
  - 字段级性能优化与动态字段是难点。
- **替代方案**：TanStack Form（保留备选）；Modular Forms（拒绝：维护停滞）。

### ADR-008：文档站自建 Vite + Solid SPA

- **状态**：已决定
- **背景**：需要真实可交互 Demo、主题/密度/RTL 切换、API 表、视觉回归；Storybook Solid 适配 beta；SolidBase 2 依赖 Solid 2 RC；solid-mdx 不成熟。
- **决策**：Vite + Solid + `@solidjs/router`，TSX 页面，`import.meta.glob` 加载 Demo，`oxc-parser` 生成 API 表，Shiki 高亮，Fuse.js 搜索。
- **后果**：
  - 与组件库同运行时；Demo 真实；完全可控。
  - 文档作者需要写 TSX；搜索/SSG 需自行实现（v1 SPA 足够）。
- **替代方案**：Storybook（拒绝）；SolidBase 2（拒绝）；Astro/VitePress（拒绝：第二框架）。

### ADR-009：三个包 + fixed versioning

- **状态**：已决定
- **背景**：内部使用需要降低版本错配；token/icon 有独立复用价值。
- **决策**：`@ui-design/tokens`、`@ui-design/icons`、`@ui-design/core`；所有包 fixed versioning。
- **后果**：
  - 依赖清晰、升级简单；包数量适中。
  - core 依赖 icons/tokens，发布需一起升版本。
- **替代方案**：单包（拒绝：token/icon 复用差）；多包（拒绝：版本复杂）。

### ADR-010：CSS 显式引入，JS 不 import CSS

- **状态**：已决定（后续可加自动引入插件）
- **背景**：隐式 CSS import 在 SSR/Webpack/Rspack/微前端下行为不一致；按需 CSS 需要可控。
- **决策**：消费者显式 `import '@ui-design/core/styles.css'` 或按组件 CSS；JS 产物不 import CSS。
- **后果**：
  - 构建行为可预测；SSR 简单。
  - 业务方可能忘记引入 CSS；需要文档/脚手架/lint 提示。
- **替代方案**：JS 内 import CSS（拒绝：副作用不可控）；CSS-in-JS（拒绝）。

### ADR-011：Chrome 最近 30 个稳定版（约 128+）

- **状态**：已决定
- **背景**：业务以 Chrome/Edge 为主；2026-11-05 本地 Chrome 157，最近 30 个稳定版约为 Chrome 128–157；不支持 IE / 旧 Chromium / 360 兼容模式。
- **决策**：Chrome 最近 30 个稳定版为硬基线；Edge 跟随 Chromium；Firefox / Safari 为 best effort（建议 Firefox 128+ / Safari 17.6+），不作为发布阻塞。启用 `@layer`、`:has()`、`color-mix()`、Container Queries、CSS Nesting、Subgrid 等现代 CSS；best-effort 浏览器用 `@supports` / PostCSS 提供渐进降级。
- **后果**：
  - 可以使用现代 CSS，减少降级与 polyfill 维护成本。
  - Firefox / Safari 不保证像素级一致，需要冒烟与已知问题清单。
  - 若业务确需 360 / 旧 Chromium，需要单独兼容层，不进入主基线。
- **替代方案**：只支持最新 Chrome（拒绝：30 版窗口更符合企业升级节奏）；兼容旧 Chromium（拒绝：成本高、阻碍现代 CSS）。

### ADR-012：MVP 范围 33 个组件，复杂组件分阶段

- **状态**：已决定（可按试点调整）
- **背景**：AntD 全量 70+ 组件，3–4 人团队无法在合理时间覆盖。
- **决策**：MVP 聚焦 CRUD 闭环（基础/表单/表格/反馈），Table/DatePicker/Form 高级能力放 v1.0。
- **后果**：
  - 快速让试点上线；部分业务需等待或自行扩展。
  - 需要严格的优先级与需求评审。
- **替代方案**：全量对齐（拒绝：延期/质量风险）。

### ADR-013：MVP 只发编译后 ESM，明确不支持 SSR；v1.0 引入 `"solid"` 双构建

- **状态**：**MVP 边界部分已被 ADR-018 取代（v0.3）**；技术依据（只发编译后 ESM 无法 hydrate）仍然成立，本节保留作为历史记录
- **背景**：v0.1 同时写了「MVP 只发布编译后 ESM」「`solid: { hydratable: true }`」「SSR / hydration 冒烟列为验收」。vite-plugin-solid 官方 README 明确：Solid JSX 在构建期按目标编译，只发编译后 JS 会锁死目标，产物为 client-only DOM，服务端渲染抛 `Client-only API called on the server side`，且无法 hydrate；解法是发布 `"solid"` 条件的 JSX 源码，由消费方按目标重新编译。
- **决策**（**已由 ADR-018 取代，以下为 v0.2 历史口径**）：当时 MVP 只发编译后 ESM、不承诺 SSR 能力，`examples/solid-start` 只做构建冒烟；Phase 1 先建立 `dist/source/*.jsx` + `"solid"` 条件的产物骨架（Phase 0 做可行性 Spike），完整 SSR 支持推到 v1.0 / Phase 6。
- **后果**（历史）：当时 MVP 范围与验收清晰，试点若用 SolidStart 需登记限制；提前建骨架避免 Phase 6 改 `exports` 结构与所有子路径导出造成破坏性变更；`hydratable` 编译选项不再被当作 SSR 保障（此点 v0.3 仍成立）。
- **替代方案**：MVP 即上双构建（当时拒绝：增加 Phase 1 复杂度）；完全放弃 SSR（拒绝：v1.0 仍需支持）。**v0.3 注**：第一条拒绝理由已被 Q17 决策推翻，现按 ADR-018 在 MVP 落地双构建。

### ADR-014：响应式值传递契约

- **状态**：已决定（v0.2 新增）
- **背景**：Solid 不重渲染组件，props 是 getter。v0.1 未定义「props 传 `T` 还是 `Accessor<T>`」、`Form.Item` 注入的 `value` 是值还是 getter，示例里 `value={userId()}` 与 `rowSelection={{ selectedRowKeys }}` 混用，Form / Table 联动无法正确实现。
- **决策**：props 值类统一接受 `T | Accessor<T>`，组件内用 `resolveValue()` 归一并在 getter 中读取；受控以 `props.value !== undefined` 判定；所有 Context 注入的 `value` / `status` / `disabled` 一律为 getter；派生用 `createMemo`，禁止 `createEffect` 同步到第二份 signal。契约写入 02 §6 与 06 §7 评审清单。
- **后果**：API 一致性可验证、Form / Table 联动正确；每个组件模板与测试需落实，增加少量 `resolveValue` 调用。
- **替代方案**：全库强制传 accessor（拒绝：业务方写起来啰嗦）；全库强制传值（拒绝：丢失响应性）。

### ADR-015：状态表达统一 `data-*`，BEM 只用于静态结构

- **状态**：已决定（v0.2 新增）
- **背景**：v0.1 中 01 §4.3 写 `.ui-button--primary` / `.ui-button--sm`，02 §5.2 写 `data-size="md"`，06 §3 模板生成 5 个 modifier class，而 06 §4 的 SCSS 只匹配 `[data-variant][data-color]` / `[data-size]` —— 模板产出的 class 是死代码，且 size 存在 `small/medium/large`、`md`、`sm` 三套取值。
- **决策**：BEM 仅用于块与元素（`.ui-button`、`.ui-button__icon`）及静态装饰（`.ui-button--block`）；所有可枚举变体与状态用 `data-*` 属性选择器；尺寸唯一口径 `small | medium | large`；06 §2.2 / §3 / §4 三处模板统一为同一份。
- **后果**：CSS 与模板一致，业务方覆盖路径清晰；发布前需按此口径重审所有组件模板。
- **替代方案**：保留 modifier class 为主（拒绝：与 data-* 双轨易错）；CSS Modules（ADR-003 已否决）。

### ADR-016：视觉回归、SSR 与性能验收按版本分档

- **状态**：已决定（v0.2 新增）
- **背景**：04 §3.2 说 MVP 不做暗色/密度/RTL 完整回归，但 04 §8 DoD、06 §5.3、05 Phase 4 都要求四套矩阵 × 3 viewport；07 §6 又要求 Phase 0 验收 Table 1 万行 60fps（该功能 Phase 5 才有）。验收标准互相冲突会直接卡住 `0.1.0` 发布。
- **决策**：MVP 基线 = light / ltr / default + 1280/768 viewport，375px 仅不溢出冒烟；dark / compact / rtl **视觉**全矩阵、Table 60fps 仍为 v1.0 门槛。**v0.3 修订（ADR-018）**：SSR 渲染与 hydration 的**单档冒烟**提前到 MVP，只有 SSR 全矩阵回归 / 流式渲染留 v1.0。Phase 0 只验可行性。
- **后果**：v0.1 可按时发布；v1.0 前必须补齐并冻结 API。
- **替代方案**：MVP 即全矩阵（拒绝：3 人 14 周不可行）。

### ADR-017：TS 7 原生二进制平台包与 tsconfig 约束

- **状态**：已决定（v0.2 新增，2026-11-05 实测）
- **背景**：实测 `typescript@7.0.2` 的 `tsc` 是 JS wrapper，实际编译器为 20 个 `@typescript/typescript-<platform>` 原生二进制包；未安装平台包时报 `Unable to resolve @typescript/typescript-darwin-arm64`。方案默认「私有 npm registry」，但没写镜像约束。另外实测 `baseUrl` 已移除（TS5102）、`rootDir` 必须显式（TS5011）、`include` 不收窄会误扫 `node_modules` 内 `.d.ts`。
- **决策**：私有 registry 必须镜像对应版本的全部平台包，CI 各架构跑 `tsc --version` 验证；`tsconfig.build.json` 强制 `rootDir: src`、`include: ["src/**/*"]`、`skipLibCheck: true`；`tsc --emitDeclarationOnly` / `declarationMap` / `jsx: preserve + jsxImportSource` 已实测通过，可作为声明产出基线。
- **后果**：CI 稳定；升级 TS 时需同步镜像新平台包。
- **替代方案**：改用 TS 6 + 传统 tsc（拒绝：不满足 TS 7 要求）；CI 固定单一架构（拒绝：与多平台构建冲突）。

### ADR-018：MVP 主力 SPA / MPA，但 SSR 必须可用 —— `"solid"` 双构建提前到 MVP

- **状态**：已决定（v0.3，2026-11-05 业务确认 Q17；**取代 ADR-013 的「MVP 不支持 SSR」边界**）
- **背景**：业务确认试点「目前准备以 SPA / MPA 应用为主，但是希望 SSR 使用正常」。即试点不强依赖 SolidStart，但组件库不能出现「服务端渲染抛 `Client-only API` / 无法 hydrate」。v0.2 的 ADR-013 把双构建放在 Phase 1 建骨架、v1.0 才正式支持，会导致 MVP 产物在 SSR 场景直接不可用。
- **决策**：
  - MVP 交付 `dist/esm`（编译后 JS）+ `dist/source/*.jsx`（保留 JSX 源码）双构建，每个含组件的 `exports` 子路径都提供 `"solid"` 与 `"import"` 条目；Phase 0 验可行性、**Phase 1 建成正式构建**（不再是骨架）。
  - M4 验收新增：`examples/solid-start` 构建 + `renderToString` + hydration 冒烟（light / ltr / default 单档），CI 检查 hydration warning；SSR-safe 编码从「约束」升为验收项。
  - 试点仍以 SPA / MPA 为主，**不引入** SSR 全矩阵视觉回归、流式渲染、Portal SSR 细则；这些留 v1.0（Phase 6）。
  - 排期：Phase 4 增 1 周（第 15 周），M4 15 / M5 22 / M6 28 / M7 29 周末，人力换算改为 MVP 15 周 / v1.0 28 周。
- **后果**：SSR 场景开箱可用，`exports` 结构在 MVP 即冻结，消除 Phase 6 破坏性变更风险；代价是 MVP 多 1 周、构建链多一条产物线与一一对应校验。
- **替代方案**：维持 ADR-013 不支持 SSR（拒绝：与业务「SSR 使用正常」冲突）；把试点整体改为 SolidStart SSR（拒绝：主力场景是 SPA / MPA，会放大排期与回归矩阵）。

### ADR-019：Button 默认 `color` = `primary`

- **状态**：已决定（v0.3，业务确认 Q16）
- **背景**：v0.2 遗留 Q16；07 原建议默认 `neutral`（贴合 03「视觉克制」），但 06 §2.2 / §3 组件模板已写 `?? 'primary'`，文档与模板不一致。
- **决策**：`color` 默认 `primary`，与现有模板一致；`neutral` 必须显式传入。视觉克制改由 `variant`（默认 `solid`，可退到 `outline` / `text`）与主色按钮出现频次控制，不靠改默认色。02 §6.1、03 §3.1、04 §6.1、06 §3 的类型注释、示例与说明同步注明。
- **后果**：模板无需改动，消除口径冲突；文档站需在主按钮使用指南中提示「一个视图内主色按钮不超过 1 个」。
- **替代方案**：默认 `neutral`（拒绝：业务已选 primary，且需改模板与 SCSS 默认值）。

### ADR-020：包名暂用 `ui-design`，许可证 MIT

- **状态**：已决定（v0.3，业务确认 Q1 / Q8）
- **背景**：品牌名尚未确定；许可证在 v0.2 标注为「待法务确认」的 MIT，影响包元数据与对外复用口径。
- **决策**：MVP / v1.0 规划期一律使用目录名与文档名 `ui-design`、npm scope `@ui-design/*`、CSS 前缀 `ui-`；**正式品牌名待发布前确定，但 scope / 前缀必须在单一常量与构建脚本中集中定义**，改名只改配置，不改组件 API。许可证定为 **MIT**：仓库根目录与各包带 `LICENSE`，`package.json` 声明 `"license": "MIT"`，发布门禁校验存在性；新增依赖仍做许可证审查。
- **后果**：命名决策不再阻塞 Phase 0；发布前改名成本可控（配置 + 文档 + import 路径的集中替换，需一次全量冒烟）。
- **替代方案**：现在就定品牌名（拒绝：业务明确「还没想好」）；`UNLICENSED` 仅内部使用（拒绝：业务已定 MIT）。

## 5. 决策流程

- **提案**：组件/API/架构变更先写 1 页说明（场景、方案、替代、影响、风险）。
- **评审**：技术负责人 + 设计 + 至少 1 名组件 owner；破坏性变更需 2 人批准。
- **记录**：结论追加到本文 ADR；不覆盖历史。
- **执行**：拆任务、加测试、加 Changeset。
- **复盘**：发布后 1 周检查 bug、性能、采用情况；必要时修订决策。

### ADR 模板

```md
### ADR-XXX：标题

- **状态**：提议 / 已决定 / 已废弃 / 被 ADR-YYY 取代
- **背景**：
- **决策**：
- **后果**：
- **替代方案**：
```
